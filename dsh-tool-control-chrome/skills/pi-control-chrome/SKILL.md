# Pi Control Chrome for DSH

Use this Skill only when the user explicitly asks to use the existing Chrome or Edge browser, its tabs, logged-in session or browser UI.

Do not activate browser tools merely because browser control might help. For ordinary public research, prefer web_search or another lightweight web capability.

After this Skill loads successfully, the pi-control-chrome plugin makes the browser_* tools available for the current Agent session. Start with browser_status, then browser_tabs or browser_selected, then browser_snapshot before acting. browser_snapshot returns one bounded semantic state with snapshot-scoped refs; it omits duplicate raw accessibility and frameTree fields from the model result and accepts optional selector, maxChars, and maxNodes. browser_accessibility_snapshot returns bounded full, incremental diff, or unchanged semantic text; the first read is full and later reads may be diff or unchanged, while disableDiffing requests a full tree. browser_extract accepts selector and a shared maxChars budget. browser_evaluate bounds returned values to depth 8, 2,000 array items, 200 object fields, and 200,000 characters; browser_console and browser_network return at most 200 entries and 20,000 serialized characters per read. All page tools return a snapshot-scoped `snapshotId`; pass it with any ref-based interaction or element-state wait. Re-snapshot after navigation or page changes. browser_status and browser operations automatically wait for the extension's background reconnect. If a result still returns `state: "bridge_only"`, follow its `nextAction` and retry browser_status once before asking the user to run `/chrome connect`; do not dispatch a browser operation while the extension is disconnected. A `bridge_offline` result means the local Bridge could not be started or reached and may require `/chrome connect`.

When one Bridge exposes multiple ready browser targets, select the intended `browserId` with `browser_status` before acting; omit `browserId` for automatic discovery when one target is ready, and blank values are treated the same as omitted. Never choose the newest connection, active window or first list entry implicitly. Keep that logical target stable. A target reconnect changes its connection generation; refresh status and inspect the page before retrying, and never automatically replay a side-effecting operation whose outcome is uncertain. Stop if the task would move to another `browserId` without explicit user selection. Never close, navigate, move or claim a user tab unless the task requires it. Preserve handoff and deliverable tabs. Do not expose passwords, cookies, access tokens or unrelated page data.

Use browser_locator, browser_cua, browser_console, browser_network, browser_dialog, browser_upload, browser_download, browser_evaluate or browser_cdp only when the user's task requires that capability. Verify destructive or externally visible actions immediately before performing them.

Prefer semantic targets for common interactions: `role` with `name`, then `label`, `placeholder`, `text`, or `testId`. A snapshot ref is scoped to the latest `browser_snapshot` or `browser_accessibility_snapshot`; pass its matching `snapshotId` to ref-based interactions, locators, and element-state waits. Keep locators in `target`, never in `handle`; omit optional fields instead of sending empty strings or `index: -1`. A semantic target must resolve to one visible element; use an explicit zero-based `index` only to resolve intentional ambiguity. Actions and `visible`/`enabled` waits apply an explicit index after visibility filtering, so hidden duplicate controls do not consume it. `browser_wait` supports `load`, `url`, `text`, `text_gone`, `visible`, `hidden`, and `enabled`; text waits use `text`, and element-state waits use the same nested `target`. `hidden` succeeds when no visible match exists; `visible` and `enabled` reject multiple visible matches. Add `url` or `urlIncludes` when the wait must remain on a particular page. For a Network response body, pass both `requestId` and the matching `loaderId` from the current listing; reacquire them after navigation.

Browser page operations also carry document identity. Complete tab handles include `tabFence` and, when the page is script-accessible, an `incarnation` derived from URL, `performance.timeOrigin`, and a per-document token. Navigation invalidates snapshot refs, DOM-CUA node ids, dialog/file-chooser observations, and Network request-loader ids. Read-only page reads may re-observe a user tab and retry once when its document changes during observation; a persistent change returns `BROWSER_PAGE_CHANGING`, so refresh `browser_tabs` before retrying the read. Side-effecting operations retain strict document fencing: if one loses its injected result or document identity, treat `BROWSER_OPERATION_UNCERTAIN` as unknown, inspect before retrying, and never replay it automatically. Automated verification should use an Agent-owned test tab or isolated browser profile instead of the active DSH GUI tab. At turn end, the host closes unmarked Agent temporary tabs, releases claimed user tabs without closing them, and detaches the current session debugger lease. Mark a tab with browser_mark_handoff or browser_mark_deliverable when it must survive the current turn; these marks are turn-scoped and must be repeated in a later turn. Use `recoverStale: true` with `browser_cleanup` only after an explicit human recovery decision following an extension runtime change; it forgets unknown-incarnation ownership records without closing those tabs and returns their ids in `recovered` for inspection. Use browser_context_reset only when the user explicitly asks to reset or clear this browser context and deactivate the lazy tools. The DSH human commands `/chrome status`, `/chrome targets`, `/chrome profile [browserId]`, `/chrome connect`, `/chrome disconnect`, `/chrome doctor`, `/chrome restart`, and `/chrome tabs` are diagnostics or lifecycle commands; they do not replace loading this Skill for model browser control.
